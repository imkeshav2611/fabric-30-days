The problem

Three teams, three reports, three revenue numbers.

1SalesCounts orders when placed
2FinanceCounts them when paid
3OperationsCounts them when shipped

Everyone is right by their own definition. The meeting is spent arguing about whose number to use.

The simple version

A shared dictionary for your data.

A dictionary does not create words. It fixes what each one means, so two people can use the same word and understand each other.

A semantic model fixes what "revenue", "active customer" and "margin" mean, once.

How it works

What a semantic model contains

1Fact tables hold events: sales, visits, readings
2Dimension tables describe them: date, product, region
3Relationships link facts to dimensions
4Measures define each KPI once, in DAX
5Reports read the model, not the raw tables
Define once, use everywhereA measure written in the model gives the same answer in every report, in Excel and to an AI agent.

What has changed recently

You create it on purpose nowFabric stopped auto-creating a default semantic model for lakehouses and warehouses. Build the model deliberately.
Storage mode is per tableImport, DirectQuery and Direct Lake can be mixed in one model.
Direct Lake is the default on Fabric dataNew models on a warehouse or SQL endpoint use Direct Lake, reading Delta tables without an import.
It is codeModels can be edited as text, versioned in Git and deployed through pipelines.
The honest part

Model it or query the tables directly?

Build a model

  • The same KPI appears in many reports
  • Business users explore the data themselves
  • An AI agent will answer questions on it

Query directly

  • A one-off analysis
  • Engineers exploring raw data
  • A single technical report

The catch: a model built on Silver-quality tables spreads bad numbers faster. The model makes a definition consistent. It cannot make it correct.

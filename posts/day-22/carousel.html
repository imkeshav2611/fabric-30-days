How it works

The layers, from wide to narrow

1Microsoft Entra ID proves who you are
2Workspace roles: Admin, Member, Contributor, Viewer
3Item permissions: share one lakehouse or report
4OneLake security: tables, folders, columns and rows
Least privilegeStart people at the narrowest layer that lets them do the job, and widen only when needed.
For engineers

Details people get wrong

Viewer is not harmlessA Viewer can query data through SQL and reports, but gets no direct OneLake file access unless a role grants it.
Contributor sees everythingAdmin, Member and Contributor can read all data in the workspace. Row-level rules do not hold them back.
OneLake security travels with the dataRoles defined on the data are enforced across Fabric engines, not only in one tool.
Use groups, not namesAssign roles to security groups. Individual assignments are impossible to audit later.
The honest part

Workspace role or finer control?

Role is enough

  • A small team that all sees the same data
  • Development workspaces
  • Everyone builds, nobody only consumes

Go finer

  • Sensitive columns such as salary
  • Different regions see different rows
  • Consumers outside the build team

The catch: the quickest fix for "I cannot see it" is making someone a Contributor. That one click bypasses every row and column rule you designed.

From real work

Security on a real project

A people-analytics platform holding sensitive employee data.

1Role-based access control decided who could reach the platform
2Row-level security limited which employees each user saw
3Sensitive personnel data stayed protected inside Fabric
4HR leaders queried it through reports and an assistant

With employee data, security is the first design decision, not the last.

The simple version

Rehearsal before the live show.

No theatre opens a play without rehearsing it. Mistakes happen on an empty stage, not in front of the audience.

Deployment stages are your rehearsal rooms, and Git is the script with every revision kept.

✓GitEvery change saved, with history
✓Dev and TestWhere mistakes are cheap
✓ProductionOnly what passed
How it works

The path of a change

1Connect the workspace to a Git branch
2Work in Dev, commit, and open a pull request
3Deploy to Test and check the result
4Deploy to Production when it passes
5Undo a bad change by reverting the commit in Git
Two tools, two jobsGit keeps the history of your items. Deployment pipelines move them between stages.
For engineers

What to set up

Git providersAzure DevOps, GitHub and GitHub Enterprise are supported, in their cloud versions.
Stages are flexibleA deployment pipeline can have from 2 to 10 stages. Three is the default.
Variable librariesKeep values that differ per stage, such as connection names, out of the items themselves.
Automate when readyThe fabric-cicd library and the Fabric CLI let a build server deploy for you.
The honest part

How much process do you need?

Minimum for everyone

  • Separate Dev and Prod workspaces
  • Everything committed to Git
  • No direct edits in production

Add when you grow

  • Automated deployments from a build server
  • Pull request reviews for each change
  • Automated tests on deployment

The catch: deployment moves definitions, not data. A lakehouse arrives in Test with its structure and no rows. Plan how each stage gets its data.

Watch out

Four things to plan for

1Item support varies: check each item type you use
2Stage-specific values such as connections and IDs
3Data in lower stages: sample, shortcut or reload
4Who may deploy to production, and who approves

The goal is boring releases. Boring is good.
